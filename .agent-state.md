# Liferay Tunnel (lfr-tunnel) — Persistent Agent State

*This document maintains continuous state across AI coding sessions and provider transitions.*

## Current Focus (as of 2026-08-25)
**All cluster-resilience work is merged. Nothing is released and nothing is deployed.** The
next two actions are a release and a five-gateway deploy; until then none of it is running
anywhere.

Eight PRs landed today (#1305, #1312, #1314, #1307, #1315, #1316, and Gemini's #1313, #1317).

**Mechanisms worth remembering:**

- **#1305 (drain) + #1306** -- a deploy dropped every tunnel it was serving. The gateway now
  announces the restart, clients migrate first, and the deploy waits for it to empty. #1306 had
  the widest blast radius: the client tore its tunnel down whenever *either* pinged endpoint
  reported eviction, so any transient central outage dropped every edge-served tunnel in the
  fleet at once -- the opposite of what regional edges are for.
- **#1312 (#1310)** -- failover set cooldowns from the start; failback never read them, so a
  client moved off by a shutdown warning was dragged back the moment that gateway answered.
  Masked for scheduled stops (the node really is off), exposed by drains. **The gate must be
  inside the prober, before it cancels** -- a first attempt put it in main.go after
  ConsumeFailback and was correct but useless, because cancelling IS the interruption.
- **#1314 (#1238)** -- a draining gateway still accepted registrations, so a client could land
  on a node seconds from restarting. healthz reports `draining`, deliberately distinct from
  `degraded` (conflating them is where #1145 came from), and registration returns 503.
- **#1307 (#1304)** -- portal sessions were in-memory, so every restart signed everyone out.
  **Behaviour change worth knowing:** getCurrentUserRaw never checked expiry, so an expired
  session still resolved a user on every /api path through it. Both paths share one store now.
- **#1315 (#1302)** -- central renews the wildcards, edges renew nothing, and nothing carried a
  renewal outward. Three scripts with privilege separation; the installer refuses a mismatched
  key, a cert for an unserved name, and any rollback to an older cert.
- **#1316 (#1300)** -- provisioning installed a Cloudflare DDNS updater on every edge and
  enabled it with the comment *"it will trigger but log a credential error until API token is
  updated"*. An updater expected to fail from birth is why nobody noticed when it began failing
  for a different reason and stayed broken two weeks. `-D` now selects the provider, default none.

**The recurring theme, now on its seventh instance: instrumentation that reports the wrong
thing.** A half-deployed transport, a stale deploy-clients, --upgrade reporting 404, an E2E
harness nothing ran, a DDNS updater exiting 0 while doing nothing, Certbot aimed at a provider
that no longer served the zone, and a red CI check that was simply a stale result from before
the fix existed. Prefer a check that proves the thing *works* -- a renewal dry run, an
authenticated control channel, a real challenge -- over one that proves it is *configured*.

## Review findings that merged unaddressed
Both of Gemini's PRs merged before their review was resolved. These are now **on master**:

- **#1313 (#1311, LDM installers)** -- two blocking findings from review, unanswered:
  1. `install.sh` never sets `LDM_LFR_TUNNEL_BIN`; only `install.ps1` does. So macOS and Linux
     rely on the symlink alone -- and macOS is where it matters, since the EDR quarantine that
     motivated #1311 is what happens when LDM gives up on discovery and downloads its own copy.
  2. `[ -d "$HOME/.ldm" ]` makes the fix order-dependent: installing lfr-tunnel *before* LDM
     leaves neither link nor variable, landing on exactly the download path #1311 exists to
     prevent. Non-blocking: the Windows hardlink uses `-ErrorAction SilentlyContinue` and cannot
     cross volumes, so it can fail silently while reporting success.
- **#1317 (#1249, cross-node proxying)** -- **review was never finished.** Shape is sound (a
  RemoteRouteResolver callback so proxy.go needs no cluster knowledge, hop cap of 2, visited-node
  list, WAF screening moved ahead of forwarding). Two findings to confirm against source:
  1. On an edge, `resolveRemoteRouteForHost` falls back to central for **any** unknown host, so
     a flood of nonexistent subdomains at an edge becomes a flood at central.
  2. It takes `edgeLeasesMu.Lock()` -- a full mutex, not a read lock -- on the request hot path,
     contending with edge registration and deregistration.

## Released in v1.47.0
Found by testing v1.46.0's failover live (epic #1164). Mechanisms worth remembering:

- **#1165 (PR #1170)** -- the failback prober and `probeFastestRegion` now read the
  `control_plane` field `/api/healthz` had been publishing since v1.46.0. Nothing consumed it,
  so the client still moved onto an edge that could not carry a session and was evicted five
  seconds later. With prevention in place, `failbackSuppression` drops from 5 minutes to 45
  seconds -- the five-minute blackout held a client on a worse region long after the edge had
  recovered, which reads as being stuck.
- **#1166 (PR #1171)** -- every region is advertised twice (`eu`/`central`, `in`/`edge-in`).
  Keying on the *name* meant a cooldown on `in` left `edge-in` electable, each edge was probed
  twice, and a failover could "move" between two names for the same host. Now keyed on the
  gateway host, with the port part of that identity but a default port normalised away.
- **#1167 (PR #1174)** -- `Registry.Register` stamped `NodeID: "control"` on every lease, so
  the portal reported all tunnels on the control plane. An edge now stamps itself, sharing the
  token-derivation with the control channel so the two cannot disagree.
- **#1168 (PR #1173)** -- client version in the TUI header, with a new-version notice. The old
  notice ran once at startup and wrote one log line, which the five-line log box discards
  within seconds; `StartVersionWatcher` now re-checks every 6 hours.
- **#1169 (PR #1172)** -- `http.ErrServerClosed` was treated as fatal and raced the signal
  handler's `os.Exit(0)`, so a clean SIGTERM usually exited 1 and systemd recorded FAILURE on
  every ordinary restart. This actively misled an investigation into an edge outage.

## Released in v1.46.0
Everything found while verifying v1.45.0's failover live, plus the bugs that surfaced
alongside it. Details on the issues; the mechanisms worth remembering:

- **#1147 (PR #1156)** -- the one that actually broke a tunnel. `r.leases` is keyed by host,
  so a re-registration replaces the entry; `CleanLease` deleted it unconditionally, so
  reaping a stale session removed the *live* session's route. The chisel tunnel stayed up
  while the URL 502'd forever. Any client re-registering for the same host inside the sweep's
  30s grace window hits it -- rare before automated failover, routine after.
- **#1145 / #1146 (PRs #1155, #1158)** -- failover and failback keyed off *different* health
  signals. `/api/healthz` answered "healthy" unconditionally, so a client failed back onto an
  edge whose control channel was down and got evicted within 5s, repeatedly. Edges now report
  control-plane connectivity; a rejected failback suppresses the prober for 5 minutes; and a
  gateway returns 410 for a session *it* reaped, so the client re-registers instead of
  heartbeating against nothing.
  - **Trap:** the "no lease" branch of `handleTunnelStatus` is load-bearing. Central holds no
    lease for any edge-hosted session, so answering an eviction code there fails over every
    edge client on every tick. The tombstone is scoped to sessions the gateway itself reaped.
- **#1148 (PR #1160)** -- `probeFastestRegion` discarded unreachable regions silently, so an
  election made while an edge was powered down was cached for 24h and failback could never
  improve on it (it only ever targets the startup primary). Such elections are now provisional
  and expire in 30 minutes.
- **#1153 (PR #1157)** -- `getActiveDomainsForRequest` returns *ranked candidates*, and five of
  seven rules return the full list. Registration consumed all of them, so one client start
  produced a lease and a reservation on every configured domain.
- **#1154 (PR #1162)** -- multi-port hostnames had a double dash. **Breaking:** multi-port
  public URLs change. A suffix arriving with a leading dash is deliberately left alone so older
  clients keep serving the host they advertise.
- **#1143 (PR #1161)** -- approval happened on GET with the token in the URL, and that link is
  emailed to `admin_notification_email`, which here is a Slack channel bridge. Now a
  confirmation page on GET and the approval on POST.
- **#1138 (PR #1159)** -- the Inspector accepted cross-origin requests on a fixed port. Origin
  and Host checks; no token, since the threat is a browser drive-by, not a network peer.

## Released in v1.45.0
- **Client failover/failback hardening (Epic #1119, PRs #1126 / #1127; #1137 / PR #1140)**
  - **#1120** `performRegistrationHandshake` exited the process on *any* registration failure,
    and both recovery paths called it, so one transient 502 from a healthy replacement region
    killed the tunnel and dropped the lease. Split into `attemptRegistration` (classifies, never
    exits) plus a fatal wrapper used only for the initial startup registration. A 403 stays
    terminal. An HTML 502 from a proxy fails at the JSON decode step and matched none of the
    gateway-error patterns, so it previously reached `log.Fatalf`; now retryable.
  - **#1121** Failover could re-elect the region it had just left, and loop. The old code deleted
    the failed region from `cfg.Regions`, but `resolveServerURL` then called `fetchRemoteRegions`,
    which replaces that map wholesale and restored the entry. The exclusion only ever held when
    the failed edge was *also* unreachable over HTTP — which it is not in the lease-eviction path,
    where the edge is up and only the lease is gone. Replaced with a cooldown applied *after* the
    refresh, rediscovery from a host other than the failed one, and bounded retry across regions.
  - **#1137** A failed failback then cooled down the region it had just logged that it was
    *staying on*, because execution fell into the failover branch with `cfg.Region` already
    restored. Both the primary and a healthy edge ended up excluded. With exactly two regions the
    candidate set emptied and `regionCooldowns.filter` returned the unfiltered map, so the client
    could re-elect the primary whose failback had just failed — the loop #1121 exists to prevent.
    Introduced by #1126 and caught in review before it ever shipped.
  - **#1122** Region/endpoint updates raced the TUI. Added `SetRegionEndpoint` / `RegionEndpoint`
    / `ConsumeFailback`, and `TEST_BUILD_FLAGS` on the `test` target.
  - **#1123** One health-check goroutine per session instead of per mapped port. Each port
    previously ran its own ticker posting an identical status report to each endpoint, raced to
    trigger the same failover, and overwrote the single `Status` field with its own result.
  - **#1124** `pkg/client/interceptor.go` hardcoded `https://tunnel.lfr-demo.se` as the central
    control plane, so self-hosted deployments POSTed their session token, region and status to a
    third-party host every five seconds. Now taken from the gateway-advertised region list, with
    no hardcoded fallback. Same treatment for the server's `lfr-demo.se` promotion fallback.
  - **#1137 (same PR)** The health-check status POST used `http.DefaultClient`, which has no
    timeout. The only thing that could release a hung request was the loop's own context — and
    that context is cancelled *by this loop*, on lease eviction. An edge that completed the TCP
    handshake and then never responded parked the one goroutine responsible for noticing the
    eviction, so no failover was triggered at all.
- **Persistent client logs (#1128 / PR #1129)** — `~/.lfr-tunnel/logs/` holds `traffic-<sub>.log`
  and `error-<sub>.log` as JSON Lines, for foreground **and** background runs. Rotated (3
  generations, 8 MiB) rather than truncated, and deliberately does not roll an empty file so
  start/stop cycles cannot flush real content through empty generations. Bodies off by default
  behind `-log-bodies`, truncated on a rune boundary.
  - **Trap worth remembering:** the background console log handle must stay a real `*os.File`.
    `os/exec` passes an `*os.File` to the child as a file descriptor but wraps any other
    `io.Writer` in a pipe serviced by a goroutine in the parent — and a detached `-background`
    parent exits right after `Start()`, killing the child's stdout. Caught by the E2E UI suite.
- **#1130 (PR #1136)** — the TUI showed a hardcoded Inspector port (wrong whenever 4040 was taken
  or `-inspector-port` was used) and a hardcoded `127.0.0.1` target host, and truncated by bytes
  rather than runes, splitting the multi-byte characters the client's own log lines contain.
- **#1125 (PR #1132) and #1131 (PR #1139)** — the concurrency work.
  - `Server.Start`/`Server.Stop` raced on `httpServer`/`redirectSrv`; now behind `httpServerMu`.
  - `handleEdgeControlWS` wrote `auth_success` to the raw conn after publishing the `safeConn`,
    letting a concurrent broadcast interleave frames on one socket.
  - `runEdgeControlChannel` spawned a reader per loop iteration, orphaning one whenever
    `pingErrChan` won the select, and split `SetReadDeadline` from `ReadJSON` across goroutines.
    gorilla/websocket permits one reader and one writer; this had neither. One reader now owns the
    read side for the connection's lifetime.
  - Three lifetime defects in the same function: the ping goroutine returned only on a write error
    or shutdown, so every read-side failure stranded one (~1150/day on a 75s reconnect cycle); the
    reader could park on the one-slot `readCh`; and the reconnect backoffs were bare `time.Sleep`,
    keeping the channel alive for up to ten seconds after `Stop`. A per-connection done channel
    and `backoffOrStop` resolve them, and `Stop` now waits on `bgWG` before closing the database.
- **#1133 (PR #1134) and #1135 (PR #1141)** — email delivery.
  - Admin alerts were silently disabled whenever `admin_notification_email` was unset, even with
    `owner.user_id` configured, because they are independent keys with no fallback and every send
    site returns early on empty. Magic links were unaffected (addressed to the user), which is why
    it presented as "some email works, some doesn't". Now defaults to `Owner.UserID`, and warns at
    startup when nobody is configured.
  - The policy that people receive everything unless they opt out, *except* a set that must be
    delivered regardless, was never expressed as a mechanism — six sites each re-derived it from
    `NotificationPrefs == "disabled"` and drifted. `emailClass` / `shouldSendTo` now decides it in
    one place. Transactional: the admin approve link, subdomain demotion, and the reservation
    expiry warning. Notification: routine admin alerts, subdomain reserved, extension approved.
    Slack (#909) may eventually replace the *notification* class; the transactional class still
    has to be delivered somehow.
- **#1117 (PR #1118)** — removed LDM dev-box power tooling. Nothing here targets `aws-1`/`aws-2`
  and the E2E suites are pure Docker Compose, yet every PR was powering off a real LDM EC2
  instance while the hourly cron powered it back on. Belongs in `liferay-docker-manager`. **#1112**
  (edge power retry/debounce) was closed as resolved by this: the `IncorrectInstanceState` churn
  was almost certainly CI fighting that cron. Reopen if it recurs on the real edge nodes.
- **#1116 (PR #1115)** — made `TestResolveServerURL_OfflineRegionFallback` hermetic. It fetched
  the live production region list and elected regions by probing real edges, so it changed verdict
  with the edge power schedule.

## Active Operational & EDR Constraints
- **Local test execution (SentinelOne EDR)**:
  - MUST use `make test` ONLY. `LFT_TEST_DIR` defaults to **`/private/tmp`** (`Makefile:9`); the
    test binary is `$(LFT_TEST_DIR)/lfr-tunnel`. Do **not** set `LFT_TEST_DIR` to
    `/private/tmp/lfr-tunnel` — that is the binary path, and pointing the directory at it produces
    `/private/tmp/lfr-tunnel/lfr-tunnel`, outside the whitelist. Assuming the whitelist covers a
    tree rather than an exact path already caused one incident.
  - FORBIDDEN: bare `go test`, and running `./bin/lfr-tunnel` or `lfr-tunneld` directly.
  - **`GOTMPDIR` is the control, not `-o`** (#1332/#1337). The toolchain links inside `GOTMPDIR`
    and only then moves the result to the `-o` path, so adding `-o` to a command does not make it
    safe. `make test` exports `GOTMPDIR` and `make edr-guard` asserts the toolchain resolved it.
  - `scripts/check-edr-safety.sh` covers `go test` **and** `go run`, across the Makefile, scripts,
    workflows, docs and helper scripts — not just bare `go test` in `.sh`/`.yml`. It treats a file
    that exports `GOTMPDIR` as having established the control, and ignores prose describing the
    rule.
  - **`make test TEST_BUILD_FLAGS=-race` is NOT known to be EDR-safe.** It writes to the same
    whitelisted path, but a race-instrumented binary is materially larger, differently hashed, and
    hooks every memory access — plausibly a distinct trigger. It has never been validated, and
    nothing in `check-edr-safety.sh` covers it. Prefer letting CI run the race detector; ask the
    owner before running it locally.
- **S1 also kills unrelated dev tooling.** A tool that suddenly looks broken or missing is often S1
  collateral, not a missing install — seen 2026-08-21 with colima (`lima not found`, later
  recovered) and Homebrew `node` (missing `libllhttp` despite `brew list` showing it). Work around
  it (`~/.nvm/versions/node/*/bin/node`) rather than reinstalling.
- **`golangci-lint` runs containerized only** —
  `docker run --rm -v "$(pwd)":/app -w /app golangci/golangci-lint:latest golangci-lint run`.
  It reliably OOMs inside the colima VM compiling the AWS SDK (`signal: killed` on
  `pkg/provisioner/aws.go`), including when scoped to a single package, because `pkg/server`
  imports `pkg/provisioner` transitively. That is a local resource limit, not a code defect —
  CI's Lint & Format Check is authoritative and has passed on every PR.
- **Use the repo's scripts** rather than hand-rolling equivalents: `scripts/create-release-tag.sh`
  for releases, `scripts/gh-issue-sync.cjs` for filing issues, `scripts/append_timestamps.py` and
  `scripts/check_docs_review.py --changed-files` for doc footers, `scripts/pre-commit-hook.sh` for
  lint, `make e2e` / `make e2e-ui` for the E2E suites.
- **Binary signing**: client binaries must be cross-compiled and signed via 1Password CLI
  (`op run -- ./bin/lfr-tunnel-ops sign`) before release/deployment.
- **Deploy targets**: `lfr-tunnel-ops.yaml` defines only `central`. Edge deploys need `-i/-u/-s`
  flags or named targets added to that file.
- **Documentation footers**: mandatory on all `.md` files, applied by `scripts/append_timestamps.py`.
